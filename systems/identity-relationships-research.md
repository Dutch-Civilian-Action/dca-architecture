## Responsibility and connection decisions

**Start with the real involvement, then decide what is reusable.** Shared identity answers who or what the party is. A minimal shared relationship reference may help other work discover the involvement, its responsible domain/person, purpose, relevant period and authoritative detail record. The domain maintains the actual arrangement, decisions and operational state. These are distinct responsibilities even when temporarily stored in the same RW base.

This is a proposal for responsibility, not a requirement to centralise every relationship. Share a contextual fact only where another use needs the same meaning. Preserve H4U's detailed handoff and agreement in Logistics; expose a reference when Fundraising or another operator needs to find the responsible person. Do not copy every pickup instruction into a shared relationship table. The conceptual shared layer spans these connected, authoritative records; it is not synonymous with the physical base named Shared Structure.

### How cross-base connections work

Airtable native linked records connect tables within a base. Start with **persistent DCA ID + fully qualified source record URL** in the receiving base, resolved through an explicit crosswalk. Use one canonical writer per fact; maintain old local records as compatibility references while current links and workflows depend on them.

For richer interfaces, publish a deliberately limited read-only identity projection and sync it into a domain base; domain tables then link to those local synced records. Native links between synced tables require the supported linked-record sync setup, not automatic name matching. The visible Team plan has documented limits of one sync source and ten synced tables per base, and no two-way sync; actual entitlements still need checking. Eleven candidate tables plus a second Projects/Needs source cannot simply be assumed available. Keep Project/Need ID references initially. Preserve retired records/tombstones so source filters or deletion do not silently remove local links. [Airtable sync documentation](https://support.airtable.com/articles/2849803278-getting-started-with-airtable-sync).

Airtable copies can repeat native table/record IDs; record ID alone is not a globally unique source key. Visible legacy IDs also require their source namespace. Preserve both source identifiers and reconcile the real shipments before assigning a common identity. Never join copies solely on an ORG/CON/SHI number or record name.
